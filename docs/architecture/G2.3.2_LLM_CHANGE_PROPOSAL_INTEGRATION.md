# EAG G2.3.2 — LLM → ChangeProposal Integration

**Design date:** 21 August 2026
**Design baseline:** [`v2.3.1-g2.3.1`](https://github.com/MenaYassa/EAG/tree/v2.3.1-g2.3.1) at `e309710a10fbcac1c90ed7005f0978c40935236d`
**Status:** **Design reconnaissance and deterministic preservation safeguard complete; the prior live EBS-015 attempt failed on exact fixture poststate, and a new live attempt requires explicit authorization.**
**Author:** Manus AI

> **Core safety principle.** An LLM may supply an advisory, schema-validated engineering decision. It must never receive direct filesystem authority. A deterministic translator is a data-conversion boundary, not an execution authority; it is followed by the existing fail-closed mutation policy, proposal-bound one-time authorization, atomic mutation runtime, receipt, and verification.

## 1. Objective

**FACT.** G2.3.1 provides an isolated, deterministic mutation boundary for one UTF-8 file at a time. Its only supported operations are `create_file` and `modify_file`; every terminal path returns a redacted `MutationReceipt`, and policy validation occurs before authorization and again immediately before the write.[1] [2] [3]

**FACT.** The governed gateway returns either a validated advisory `EngineeringDecision` or a safe failure. The gateway itself neither executes capabilities nor writes a workspace.[4]

**INFERENCE.** The remaining safety gap is not an additional filesystem mechanism. It is the controlled conversion of a successful governed decision into a non-executable `ChangeProposal` while preserving decision identity, context provenance, repository snapshot binding, and deterministic limits.

**RECOMMENDATION.** G2.3.2 should add only a narrow, explicit, opt-in orchestration seam for one controlled proposal in a disposable workspace:

```text
read-only Repository Context
          ↓
Governed LLM Gateway
          ↓  success + schema + decision policy only
EngineeringDecisionResult
          ↓
Deterministic DecisionToChangeProposalTranslator
          ↓
ChangeProposal (untrusted input)
          ↓
MutationPolicyValidator
          ↓
MutationAuthorizer
          ↓
GovernedMutationRuntime
          ↓
MutationReceipt + deterministic verification
          ↓
Sanitized outcome for a later reflection/memory handoff
```

No stage is permitted to skip a later gate. The translator may not call mutation, shell, Git, network, credential, capability, reflection, or memory APIs.

## 2. Current Architecture

**FACT.** Repository intelligence constructs bounded, redacted `EngineeringContext` from a read-only snapshot and inserts `snapshot_fingerprint` and `context_fingerprint` into context provenance and truncation metadata. Its projection explicitly tells the provider that context is read-only and that provider output is not authorized to modify the repository.[5]

**FACT.** `GatewayRuntime.decide()` performs provider execution, strict parsing, and `validate_decision_policy()` before it returns `EngineeringDecisionResult(success=True, decision=...)`. A provider timeout, schema error, budget failure, or decision-policy rejection returns a safe failure result rather than a decision.[4] [6]

**FACT.** The existing `DecisionToPlanTranslator` maps a validated `EngineeringDecision` to a generic `Plan`. The current Coordinator then maps `PlanStep.metadata` directly into a generic `CapabilityRequest` before its post-execution validation step.[7] [8]

**FACT.** A generic `CapabilityRequest` contains an arbitrary parameter mapping. The existing `WorkspaceCapability` can consume `operation`, `path`, and `content` from that mapping and may write text after creating parent directories. It has no mutation proposal, sensitivity check, precondition, authorization binding, receipt, or atomic compensation contract.[9] [10]

**RECOMMENDATION.** G2.3.2 must not send a model-derived mutation step through `DecisionToPlanTranslator → Coordinator → CapabilityRuntime → WorkspaceCapability`. That path remains valid for its legacy non-mutation uses, but is an explicit bypass of the G2.3.1 boundary for mutation.

| Current component | Current responsibility | G2.3.2 treatment |
|---|---|---|
| Repository context assembler | Creates read-only bounded evidence and freshness fingerprints. | Reuse as trusted evidence source; do not change selection or sensitivity policy. |
| Governed gateway | Returns a validated advisory decision or safe failure. | Reuse only after `success=True`; do not make it a mutation service. |
| Decision-to-plan translator | Converts a decision to generic plan steps. | Preserve unchanged for non-mutation plans; do not use it to create a mutation request. |
| Coordinator / `CapabilityRuntime` | Executes generic capability requests. | Leave unchanged in G2.3.2; do not grant raw workspace write dispatch. |
| `WorkspaceRuntime` / `WorkspaceCapability` | General workspace read/write primitive. | Do not use as an authorization substitute or direct LLM target. |
| G2.3.1 mutation package | Proposal policy, one-time authorization, atomic mutation, receipts, events. | Reuse unchanged as the sole mutation authority. |
| Autonomous loop, reflection, memory | Runs Chief, then reflects and stores reflection. | Define a future sanitized evidence handoff only; do not modify them in G2.3.2. |

## 3. Existing Contracts

**FACT.** `EngineeringDecision` is immutable and advisory. It contains an interpreted goal, assumptions, approach, ordered plan, required capabilities, risks, confidence, and grounding references. Each proposed plan step has an ID, title, capability ID, dependencies, free-form parameters, and expected evidence.[6]

**FACT.** Gateway policy enforces capability allowlists, unique step IDs, dependencies referring only to earlier proposed steps, exact required-capability alignment, executable-parameter key rejection, and repository-context grounding-reference subset checks.[11]

**FACT.** `ChangeProposal` is immutable and non-executable. It already carries `run_id`, `decision_id`, target, operation, full replacement content, exact precondition, reason, provenance IDs, risk, expected postcondition, context/repository/workspace fingerprints, and a deterministic digest.[1]

**FACT.** `MutationAuthorizer` binds authorization to the exact proposal ID/digest, target, operation, workspace fingerprint, repository snapshot fingerprint, and policy version, then permits exactly one successful consume operation.[2]

**FACT.** `GovernedMutationRuntime` publishes proposal/authorization/start/terminal lifecycle events, revalidates policy state before consumption, writes atomically with a temporary file and `os.replace`, and yields a content-free receipt on success, policy rejection, authorization rejection, write failure, or verification failure.[3] [12]

**INFERENCE.** Existing trusted data is sufficient to bind a proposal after its content and target have been determined: `run_id` comes from the public run context, decision identity can be a deterministic digest until a first-class identifier exists, grounding references are supplied by decision policy, and snapshot/context fingerprints exist in the original request context. The missing concern is the LLM-shaped declaration of a bounded mutation intent, not another authorization or filesystem contract.

## 4. Decision → Proposal Boundary

**RECOMMENDATION.** Add a dedicated `DecisionToChangeProposalTranslator` adjacent to the existing gateway translation layer, for example `src/eag/chief/intelligence/gateway/mutation_translator.py`. It should depend on gateway-domain models and the public mutation-domain models, but the `eag.mutation` package must remain independent of gateway/provider code.

> The translator is a pure-or-read-only conversion service. It turns a **successful, policy-validated gateway result plus trusted execution state** into `ChangeProposal` data. It is not a capability, filesystem writer, authorizer, or provider caller.

**RECOMMENDATION.** The translator should accept a single explicit request object containing the following trusted and untrusted values:

| Input | Source | Required translator handling |
|---|---|---|
| `EngineeringDecisionResult` | Gateway | Require `success=True`, `decision is not None`, and no policy violation/error. Reject all other result states. |
| Original `EngineeringDecisionRequest` | Gateway caller | Use its context provenance and `truncation_metadata` as the authoritative context/snapshot binding. |
| `RunContext` | Public Chief/run caller | Copy `run_id`; do not accept an LLM-provided run identity. |
| Explicit mutation-mode policy | Trusted composition | Require a dedicated opt-in and a fixed capability/operation allowlist. |
| Read-only target-state reader | Trusted workspace facade | Read exactly the declared target to derive existence and current fingerprint. It must not call write, shell, Git mutation, network, or credentials. |
| Decision identity function | Deterministic local function | Compute a stable digest from canonical validated decision data and request ID until the decision contract has a first-class ID. |

**RECOMMENDATION.** Translation must occur **after** `GatewayRuntime.decide()` has produced a successful validated result and **before** `DecisionToPlanTranslator` or any generic `CapabilityRequest` is constructed for the mutation step. A translated proposal is still untrusted and must subsequently be passed unchanged through `GovernedMutationRuntime.validate()`, `authorize()`, and `mutate()` or its existing one-call `execute()` composition.

## 5. Translation Contract

**RECOMMENDATION.** The future translator should expose a narrow outcome type, not return an exception-shaped generic dictionary. Its terminal results should be either `TranslationSucceeded(proposal=...)` or `TranslationRejected(code, sanitized_reason, decision_id, run_id, step_id)`. No translated raw content belongs in events, logs, failures, receipts, reflection, or memory.

The translator’s deterministic steps should be:

1. Require a successful `EngineeringDecisionResult`; reject provider, routing, schema, budget, and gateway-policy failures without attempting translation.
2. Verify the decision schema version and the dedicated mutation-intent contract version accepted by composition.
3. Select exactly one declared mutation intent using a deterministic rule. G2.3.2 must reject zero, more than one, or duplicate intents.
4. Require the declared mutation capability to be in the original request allowlist and fixed to the dedicated governed mutation capability identifier.
5. Lexically validate the target as a normalized relative POSIX path. Reject absolute paths, `..`, NUL, backslashes, empty components, and ambiguous target forms before reading it.
6. Require an unambiguous first-slice operation. For the first live scenario, support only `modify_file`; reserve `create_file` for a later separately approved scenario.
7. Require exactly one complete UTF-8 replacement-content value, bounded before any target-state read. Reject partial edits, unified diffs, find/replace instructions, commands, tests, code blocks outside the field, and free-form operation descriptions.
8. Derive the precondition from trusted current target state. For a modify request, the target must exist as a safe regular UTF-8 file and its exact fingerprint becomes `MutationPrecondition(expected_exists=True, expected_fingerprint=...)`.
9. Derive `MutationPostcondition(expected_exists=True, expected_fingerprint=content_fingerprint)` deterministically. Do not accept a model-supplied test command, parser invocation, or arbitrary verification instruction.
10. Copy `run_id`, deterministic decision ID, context fingerprint, repository snapshot fingerprint, the ordered grounding references, reason, and a conservative risk category into `ChangeProposal`.
11. Return the immutable proposal without calling mutation policy, authorization, write, generic capability dispatch, shell, Git, network, reflection, or memory.

**RECOMMENDATION.** The translator should be deterministic with the same validated decision, original request, trusted target state, and composition policy: it must emit byte-for-byte equivalent proposal fields and digest. It must be stateless and must not remember prior authorizations or retries.

## 6. EngineeringDecision Requirements

**FACT.** The current decision schema does not have a decision ID, a typed mutation intent, target path, allowed mutation operation, full replacement content, trusted precondition, mutation verification model, or a proposal-set identity.[6]

**FACT.** The generated JSON schema has strict `additionalProperties: false` for a proposed plan step but does not expose `parameters` as a schema property, even though the parser can accept an optional parameters mapping. Therefore `parameters` are neither a stable nor a safely typed LLM interface for a controlled file mutation.[11]

**CONCLUSION.** The existing `EngineeringDecision` schema is **not sufficient** to express the first controlled mutation slice safely. Reusing `PlanStep.parameters` would be ambiguous, under-specified, and would recreate the generic parameter-to-workspace-write bypass.

**RECOMMENDATION.** Do not change the existing advisory decision schema opportunistically. In a separately approved implementation, introduce a versioned, mutation-only decision extension or a distinct request/result contract with this minimal typed envelope:

| Field | Producer | Purpose | Translator treatment |
|---|---|---|---|
| `mutation_intent_id` | LLM | Unique declared intent identifier. | Require non-empty and unique; preserve as provenance metadata only. |
| `plan_step_id` | LLM | Links intent to the validated ordered decision step. | Require an existing step and exact match to the mutation step. |
| `target_path` | LLM | Workspace-relative target declaration. | Lexically validate, then let mutation policy enforce filesystem safety. |
| `operation` | LLM | `modify_file` only in the first live scenario. | Require exact enum; reject every other operation. |
| `replacement_content` | LLM | Complete proposed UTF-8 file content. | Treat as untrusted; fingerprint and never publish raw content. |
| `reason` | LLM | Bounded rationale. | Preserve only under bounded length; may use plan title/approach as fallback. |
| `grounding_references` | LLM decision | Links intent to selected repository evidence. | Require non-empty subset of the original request context provenance. |

The following data must remain translator- or policy-derived rather than LLM-declared: precondition fingerprint, postcondition fingerprint, content byte count, decision digest, run identity, workspace fingerprint, repository snapshot fingerprint, authorization state, target safety classification, verification result, receipt, and rollback status.

## 7. Proposal Generation

**RECOMMENDATION.** G2.3.2 must translate **exactly one** validated mutation intent into **exactly one** `ChangeProposal`. It should not translate a generic plan, the decision’s non-mutation steps, or a collection of arbitrary proposals.

**RATIONALE.** The G2.3.1 runtime is deliberately single-file and uses conditional compensation, not a multi-file transaction. A one-intent/one-proposal rule preserves atomicity, makes preconditions local and exact, ensures one authorization is consumed at most once, and creates one auditable receipt.

| Decision shape | G2.3.2 translator result |
|---|---|
| One supported, grounded, mutation intent with no mutation-step dependencies | One proposal candidate; continue to policy. |
| No mutation intent | Rejected translation; no policy call, authorization, or mutation. |
| Two or more mutation intents | Rejected as a multi-proposal request; no ordering inference or partial execution. |
| One intent with dependencies | Rejected in the first slice; no prerequisite execution exists within the mutation transaction. |
| Non-mutation generic plan steps | Ignored only if they are not the declared mutation intent and no execution route is selected; they must not be dispatched as part of this workflow. |
| Same target expressed more than once | Rejected as conflicting/ambiguous. |

**RECOMMENDATION.** Ordered proposal sets, dependency graphs, multi-file commit groups, partial success, and cross-proposal rollback belong to **G2.4 or later**, after a transactional model, proposal-set receipt, dependency-aware preflight, snapshot policy, and recovery semantics are designed and tested. They must not be inferred from the current `PlanStep.dependencies` graph.

## 8. Proposal Validation

**FACT.** G2.3.1 already rejects malformed, absolute, traversal, escaping, symlink, sensitive, oversized, stale, unsupported, and authorization-mismatched proposals. It also rechecks the target immediately before the write.[2] [3]

**RECOMMENDATION.** Translation checks are an early rejection layer; they are never a replacement for mutation policy. The required chain is:

```text
validated gateway decision
  → deterministic translation checks
  → ChangeProposal
  → MutationPolicyValidator.validate()
  → MutationAuthorizer.authorize()
  → GovernedMutationRuntime.mutate()
```

The translator should reject representational ambiguity. `MutationPolicyValidator` should continue to own filesystem confinement, sensitivity, target class, size limits, and stale precondition enforcement. This avoids duplicating security rules in a gateway-facing module and ensures non-LLM callers remain subject to the same mutation policy.

## 9. Authorization

**FACT.** Authorization in G2.3.1 is exact and one-time. A consume operation checks the proposal ID/digest, target path, operation, workspace fingerprint, repository snapshot fingerprint, and policy version; it returns a consumed immutable authorization or a typed rejection.[2]

**RECOMMENDATION.** The G2.3.2 workflow must not issue an authorization while the model is running, while its result is malformed, or before policy validation succeeds. The sequence must remain:

```text
Gateway success
  → translation success
  → policy-approved proposal
  → authorization issued
  → immediate policy revalidation
  → authorization consumed once
  → atomic mutation
```

**RECOMMENDATION.** A caller must never construct or supply an authorization from LLM output. The translator returns only a proposal. The orchestrator owns the existing policy/authorizer/runtime composition and retains receipt delivery. A proposal altered after translation necessarily has a new digest and fails authorization matching.

## 10. Mutation Boundary

**FACT.** The current mutation runtime is self-contained and intentionally has no gateway, Chief, Coordinator, Planner, `CapabilityRuntime`, shell, Git, network, or credential dependency.[1] [3]

**RECOMMENDATION.** Preserve that architectural direction. G2.3.2 should introduce an explicit public composition facade, for example `GovernedDecisionMutationWorkflow`, that receives already-composed gateway, translator, read-only state reader, and `GovernedMutationRuntime`. The facade may coordinate calls but must not expose raw workspace paths/content as generic capability parameters.

The facade’s public terminal result should contain the redacted gateway trace ID, deterministic decision ID, proposal digest, `MutationReceipt`, and sanitized translation/mutation outcome. It must not contain raw provider content, prompts, source content, a shell transcript, credentials, or a generic capability request.

**RECOMMENDATION.** `WorkspaceRuntime.write`, `WorkspaceCapability.execute`, and the current generic `Coordinator._execute_plan` path are explicit **non-targets** in this slice. They remain unchanged. Mutation calls occur only through `GovernedMutationRuntime` against an injected disposable workspace root.

## 11. Verification

**FACT.** G2.3.1 verification compares the observed post-write UTF-8 content fingerprint to the proposal content fingerprint and the bounded expected postcondition. A mismatch yields a failed receipt and performs conditional compensation only while the target still equals the observed post-state.[3]

**RECOMMENDATION.** The first G2.3.2 scenario should use only this deterministic file-level verification plus a fixture-specific in-process textual assertion. It must not run a shell test command, package manager, compiler, formatter, Git command, or model review.

The live benchmark evaluator may compare the fixture’s before/after target bytes, expected target fingerprint, changed path set, receipt fields, and lifecycle events from outside the mutation runtime. It must not add a second, uncontrolled write path.

## 12. Reflection

**FACT.** `AutonomousLoopRuntime` runs a Chief execution and then builds `ReflectionContext` from `RunResult` before calling `ReflectionRuntime.reflect()`. Reflection currently has no mutation-receipt field.[13] [14]

**RECOMMENDATION.** G2.3.2 should define, but not yet wire, a sanitized `MutationEvidenceSummary` handoff. It should contain receipt ID, proposal/decision IDs or digests, relative target path, operation, terminal result, stable failure code, verification boolean, rollback boolean, byte counts, and policy version. It must omit content, diff, preimage, absolute paths, prompt, provider response, credentials, and unbounded errors.

**RECOMMENDATION.** The future `MutationReceipt → Reflection` handoff belongs at the public autonomous iteration boundary after the governed workflow returns and before `ReflectionRuntime.reflect()` is invoked. It must be implemented through a public `ReflectionContext` extension or separate immutable evidence object, not by private runtime-field mutation.

## 13. Memory

**FACT.** The current autonomous loop passes reflection output to `MemoryRuntime.store_reflection()`. Memory runtime persists a summary and bounded outcome metadata derived from reflection, not direct execution artifacts.[13] [15]

**RECOMMENDATION.** `Verification → Engineering Memory` should continue to flow through reflection:

```text
MutationReceipt + deterministic verification
  → sanitized mutation evidence in ReflectionContext
  → ReflectionReport
  → MemoryRuntime.store_reflection()
```

Direct persistence of raw proposal or receipt content into memory is prohibited. G2.3.2 should not alter `MemoryRuntime`; a later milestone should explicitly determine memory retention, retrieval, and redaction policy for mutation outcomes.

## 14. Failure Handling

**RECOMMENDATION.** Every failure is terminal for the first live mutation attempt. There is no automatic repair, retry-by-editing, fallback mutation, rerun with changed input, or self-healing loop.

| Failure mode | Required G2.3.2 behavior | Mutation outcome |
|---|---|---|
| Provider timeout, refusal, routing failure, budget failure | Gateway returns safe failure; translator is not called. | No proposal, authorization, or mutation. |
| Schema failure | Gateway returns safe failure. | No proposal, authorization, or mutation. |
| Gateway policy rejection | Preserve sanitized policy violation metadata only. | No proposal, authorization, or mutation. |
| Successful decision lacks one typed mutation intent | Translation rejects with stable reason. | No policy call, authorization, or mutation. |
| Unsupported operation or ambiguous edit form | Translation rejects. | No mutation. |
| Invalid/absolute/traversal target | Translation rejects; policy would also reject if reached. | No mutation. |
| Target absent/wrong type/sensitive/symlink | Mutation policy rejects after trusted state check. | Rejected receipt; no write. |
| Target changes after translation | Mutation policy revalidation detects stale precondition. | Rejected receipt; no write. |
| Oversized content | Translation may reject by trusted bound; policy is authoritative. | Rejected receipt; no write. |
| Multiple/conflicting proposals | Translation rejects entire set. | No partial mutation. |
| Authorization mismatch/reuse | Existing authorizer rejects. | Rejected receipt; no write. |
| Atomic write error | Existing runtime returns failed receipt. | One failed attempt; no automatic retry. |
| Verification failure | Existing runtime returns failed receipt and conditionally compensates only when safe. | Stop; no second proposal. |

## 15. Security Boundaries

**RECOMMENDATION.** G2.3.2 must retain the following non-negotiable invariants:

| Boundary | Required invariant |
|---|---|
| LLM authority | The LLM produces only advisory structured data. It never receives a filesystem handle, shell, Git, network, credential, or authorization token. |
| Translator | It is deterministic and non-mutating. It cannot issue authorization or execute a capability. |
| Proposal | It remains untrusted even when derived from a validated decision. It carries no authority. |
| Policy | It remains fail-closed and is the authoritative filesystem/content/sensitivity/precondition gate. |
| Authorization | It is issued only after policy pass, bound to exact proposal state, and consumed once. |
| Mutation | It remains a bounded single-file atomic runtime with receipts and conditional compensation. |
| Observability | Events, receipts, benchmark diagnostics, reflection, and memory hold only redacted bounded metadata. |
| Repository scope | All design and future live testing use a disposable fixture workspace; the EAG repository is never a mutation target. |

**RECOMMENDATION.** Preserve the following counters in the eventual live EBS-015 result, with a clear definition that a governed provider request is tracked separately from mutation-side network capability use:

```text
REAL_PROVIDER_CALLS=1                # explicit live-lane precondition
CAPABILITY_EXECUTIONS=0              # expected for the direct G2.3.1 mutation runtime path
WORKSPACE_MUTATIONS=1                # exactly the approved target write
GIT_MUTATIONS=0
SHELL_INVOCATIONS=0
NETWORK_INVOCATIONS=0                 # mutation/capability-side operations; provider call is separate
OUTSIDE_WORKSPACE_MUTATIONS=0
```

## 16. EBS-015 — First Live Governed Mutation

**RECOMMENDATION.** The first live EBS-015 should be an explicit opt-in test against a copied disposable fixture repository, never `/home/ubuntu/EAG` or the checked-out source worktree.

The fixture should contain exactly one safe target:

```python
# greet.py

def greet() -> str:
    return "Hello"
```

The bounded goal should be: **“Change `greet()` in `greet.py` so it returns exactly `Hello, EAG!`; modify no other file.”** The expected after-state is the single full-file replacement with the new literal.

| Stage | Required observable assertion |
|---|---|
| Fixture preparation | Runner copies a fixed fixture to a temporary workspace and records before manifest/fingerprint. |
| Context | G2.2 assembles read-only context for that temporary root; target provenance and snapshot/context fingerprints are available. |
| Gateway | Explicit live opt-in makes one governed provider request. A failure/timeout is a benchmark failure or unresolved execution, never a pass. |
| Decision | Gateway returns a successful policy-validated decision containing one typed `modify_file` mutation intent grounded in supplied provenance. |
| Translation | Deterministic translator returns one `ChangeProposal` with trusted stale precondition and fixed target. |
| Policy and authorization | Both pass exactly once; authorization becomes consumed exactly once. |
| Mutation | One `modify_file` applies only to `greet.py`; no generic workspace capability is dispatched. |
| Receipt and verification | Completed receipt has expected pre/post fingerprints and successful verification; changed-path set is exactly `{greet.py}`. |
| Isolation | Original EAG worktree is byte-for-byte unmodified; temporary fixture is cleaned by the benchmark runner. |

**RECOMMENDATION.** EBS-015 live must be disabled by default behind an explicit environment opt-in. It must not be run during G2.3.2 design or normal test execution. A provider timeout, malformed decision, policy rejection, translation rejection, authorization rejection, or failed receipt must be reported by stage with sanitized metadata and must not trigger another provider call or repair attempt.

## 17. Test Strategy

**RECOMMENDATION.** Add tests only after this design is separately approved. The future suite should separate pure translation tests, existing mutation-boundary regression tests, composed deterministic workflow tests, and an explicit live EBS lane.

| Layer | Required future tests |
|---|---|
| Translator unit | Reject non-success gateway result, malformed typed intent, unsupported operation, zero/multiple intent, ambiguous target, invalid target, absent target, wrong target type, oversized content, missing/unknown provenance, non-empty dependencies, and tampered deterministic inputs. |
| Determinism | Same validated result/request/state produces equivalent proposal digest; changed content or target state changes the proposal/precondition. |
| Binding | Preserve run, decision digest, context, repository snapshot, and grounding provenance; LLM cannot provide trusted fingerprints or authorization state. |
| Mutation regression | Preserve all G2.3.1 path traversal, absolute path, symlink, sensitivity, operation, stale, authorization reuse/tamper, policy-bypass, receipt, event, atomicity, and no-shell/Git/network tests.[16] |
| Composed fixture | Fixed validated mutation decision → translation → policy → authorization → mutation → receipt → verification against a copied fixture, with no provider. |
| Live EBS-015 | Explicit opt-in only; one real provider call, isolated fixture before/after comparison, exact counter assertions, and no EAG-worktree mutation. |
| Regression | Existing G2.0/G2.1/G2.2/G2.3.1 suites remain unchanged; EBS-014 is not rerun as part of this work. |

## 18. Migration

**RECOMMENDATION.** Implement only after formal approval, in this order:

1. Add a versioned mutation-intent structured-output contract without weakening the existing non-mutation `EngineeringDecision` contract.
2. Add deterministic translator domain models/errors/events and pure/read-only unit tests.
3. Add a public composition facade that consumes a successful `EngineeringDecisionResult` and invokes the existing G2.3.1 runtime.
4. Add copied-fixture deterministic composition tests.
5. Add the explicit live EBS-015 lane with strict provider opt-in and counter instrumentation.
6. Consider a public Chief/Coordinator integration only after the direct composed workflow has deterministic and live evidence.
7. Defer multi-proposal ordering, generic capability integration, autonomous-loop reflection/memory ingestion, transactions, and repair behavior to later scoped milestones.

**RECOMMENDATION.** Do not modify `DecisionToPlanTranslator`, `Coordinator`, `ChiefRuntime`, `AdaptivePlanner`, generic `CapabilityRuntime`, `WorkspaceRuntime`, `WorkspaceCapability`, reflection, memory, or the existing mutation runtime as a shortcut in the first G2.3.2 implementation slice.

## 19. Risks

| Risk | Consequence | Design mitigation |
|---|---|---|
| Model emits a valid decision but a malicious mutation declaration | Unsafe target/content pressure. | Treat declaration as untrusted; translator checks representation and existing mutation policy/authorization enforce stateful safety. |
| Generic plan path accidentally handles a mutation step | Bypass of policy/authorization/receipt. | Keep mutation outside plan-to-capability translation; use an explicit dedicated facade. |
| Schema extension weakens advisory decision safety | Broader unintended provider authority. | Version mutation intent separately, strict fields/enums, and explicit opt-in. |
| Stale repository/context evidence | Overwrite of changed target. | Derive exact precondition at translation and revalidate inside existing mutation runtime. |
| More than one proposed file change | Partial application or ambiguous ordering. | Reject all multi-proposal cases in G2.3.2. |
| Sensitive source/prompt/receipt leakage | Credential or proprietary-data exposure. | Reuse context sensitivity policy; redact events, receipts, reflection, and memory; do not log content. |
| Provider unreliability | False acceptance conclusion. | Live lane is explicit and separately classified; timeout is neither PASS nor implementation proof. |
| Benchmark mutates EAG source | Repository corruption. | Fixture-manager temporary root; before/after assertions; source root prohibited. |

## 20. Non-Goals

G2.3.2 design does **not** authorize implementation of direct LLM filesystem access, source modifications, generic plan-step mutation dispatch, `WorkspaceCapability` changes, `WorkspaceRuntime` changes, Coordinator/Chief/Planner/AdaptivePlanner modifications, gateway provider configuration changes, provider retries, live EBS-015 execution, EBS-014 reruns, shell commands, Git mutations, commits, pushes, branches, network tools, credentials access, tests/formatters launched through shell, automated repair, autonomous iterative editing, multi-file mutation, delete/rename/move/copy, directory creation, transaction groups, reflection redesign, memory redesign, or benchmark-framework redesign.

## 21. Definition of Done

A future G2.3.2 implementation is complete only if all statements below are demonstrably true:

- A successful, schema- and policy-validated gateway decision with one typed mutation intent produces one deterministic `ChangeProposal`.
- The translator rejects gateway failures, unsupported or ambiguous mutation forms, multiple intents, invalid targets, and ungrounded intents without executing anything.
- Proposal fields preserve run/decision/provenance/context/repository bindings and derive pre/post fingerprints from trusted state and content, not model assertions.
- No generic `PlanStep` or `CapabilityRequest` provides a mutation bypass.
- The existing G2.3.1 mutation policy, one-time authorization, atomic runtime, receipt, and lifecycle-event contracts are reused unchanged or strengthened, never bypassed.
- The live EBS-015 fixture mutates exactly one approved file in a disposable workspace and proves the required receipt/verification/counter assertions.
- LLM-driven mutation remains opt-in; a provider timeout or rejection is not reported as acceptance PASS.
- EBS-014 is not rerun by this milestone.
- G2.0, G2.1, G2.2, and G2.3.1 regression behavior remains intact.
