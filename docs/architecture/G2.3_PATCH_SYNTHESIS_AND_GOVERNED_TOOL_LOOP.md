# EAG G2.3 — Patch Synthesis & Governed Tool Loop

**Design date:** 20 August 2026
**Design baseline:** [`v2.2.0-g2.2`](https://github.com/MenaYassa/EAG/tree/v2.2.0-g2.2) at `c7e361be7fef3a51871291b1cf94b4cdb05ec186`
**Status:** **Design reconnaissance complete; G2.3.1 deterministic mutation foundation complete; LLM and autonomous-path integration deferred.**
**Author:** Manus AI

> **Scope boundary.** G2.3 is the first proposed, deliberately narrow mutation milestone. An LLM may propose structured changes, but it must never receive shell access, direct filesystem write access, Git mutation access, network access from the mutation capability, credentials, or the ability to bypass deterministic policy and explicit capability authorization. This document is a design artifact only; it does not implement a proposal generator, mutation capability, patch engine, benchmark, or mutation.

## 1. Objective

**FACT.** G2.2 makes it possible to construct a bounded, provenance-bearing, read-only `EngineeringContext` for a repository. The existing G2.1 gateway returns a validated but advisory `EngineeringDecision`; its translator produces a deterministic Chief `Plan` without executing it.[1] [2]

**INFERENCE.** The next safety boundary is not “let the model edit files.” It is a controlled transition from **LOOK → UNDERSTAND → REASON** to **LOOK → REASON → PROPOSE CHANGE → AUTHORIZE → MUTATE → VERIFY**.

**RECOMMENDATION.** G2.3 should introduce a first-class, non-executable `ChangeProposal` and an authorization-gated, minimal text-mutation path:

```text
EngineeringDecision
        ↓  deterministic translator
Plan
        ↓  constrained proposal synthesis
ChangeProposal
        ↓  deterministic proposal policy
AuthorizedChange
        ↓  CapabilityRuntime allowlist
Workspace mutation
        ↓
MutationReceipt
        ↓
Deterministic verification → reflection / memory evidence
```

No arrow may be skipped. In particular, a `PlanStep` must not become a raw `CapabilityRequest` for a file write until the proposal is validated, authorized, and bound to the current workspace/repository state.

## 3. Current Gaps

**FACT.** The existing Coordinator executes `PlanStep` metadata through `CapabilityRuntime` before its validator runs. Its validation is post-execution, not a mutation proposal policy or authorization gate.[6]

**FACT.** `WorkspaceCapability` accepts a free-form `operation`, `path`, and `content`; its fallback write can construct a local path and write it directly. It does not hold a precondition, content bound, authorization token, diff summary, path classification, receipt, or rollback record.[4]

**FACT.** Current `CapabilityRequest` holds only a capability ID, goal text, and free-form parameter mapping. It does not bind a request to a decision, plan, proposal digest, workspace fingerprint, repository fingerprint, or authorization consumption state.[5]

**INFERENCE.** A safe mutation loop cannot be produced by merely adding fields to `PlanStep.metadata`. That would keep the current direct execution bypass.

**RECOMMENDATION.** G2.3 needs five narrow additions: (1) proposal domain models and validator, (2) mutation authorization/binding, (3) a minimal authorized workspace mutation adapter, (4) mutation receipt and verification contracts, and (5) explicit integration into the autonomous path only for approved mutation steps. It must not replace Coordinator, Chief, Planner, Gateway, Scheduler, or G2.2 repository intelligence.

## 4. ChangeProposal Contract

**RECOMMENDATION.** Introduce immutable G2.3 domain types distinct from every existing execution type.

| Type | Meaning | Must not be confused with |
|---|---|---|
| `EngineeringDecision` | LLM advisory reasoning and ordered intent. | A file change or authority to execute. |
| `Plan` | Deterministic step graph translated from a validated decision. | A patch, authorization, or receipt. |
| `ChangeProposal` | Untrusted, structured description of one bounded file mutation. | A `CapabilityRequest` or completed write. |
| `AuthorizedChange` | One-time authorization binding a validated proposal digest to current state and operation. | A generic approval or unconstrained capability request. |
| `CapabilityRequest` | Internal dispatch request constructed only from `AuthorizedChange`. | Model-controlled parameters. |
| `MutationReceipt` | Immutable result of a performed or failed mutation attempt. | A proposed diff, source content, or Git commit. |

A `ChangeProposal` should contain the following logical fields.

| Field | Requirement |
|---|---|
| `proposal_id`, `run_id`, `decision_id`, `plan_id`, `plan_step_id` | Stable audit linkage. `decision_id` may be a deterministic decision digest if the existing decision has no identity field. |
| `context_fingerprint`, `repository_snapshot_fingerprint`, `workspace_fingerprint` | Bind the proposal to G2.2 evidence and current target state. |
| `target_path` | Normalized workspace-relative POSIX path only. No absolute path or parent traversal. |
| `operation` | First-slice enum: `CREATE_UTF8_TEXT` or `REPLACE_UTF8_TEXT`. |
| `precondition` | Target-existence expectation plus expected pre-fingerprint or expected absence. |
| `proposed_content` | Complete UTF-8 replacement content, held only until authorized write; never placed in events/receipts/memory by default. |
| `proposed_content_fingerprint`, `bytes_proposed`, `line_count` | Deterministic policy and receipt inputs. |
| `reason`, `provenance_ids`, `risk` | Bounded rationale tied to supplied G2.2 provenance identifiers and explicit risk category. |
| `expected_postcondition` | Deterministic, bounded statement such as post-fingerprint and expected existence; not arbitrary natural-language test instructions. |
| `authorization_metadata` | Empty before authorization; afterward only an `AuthorizedChange` reference/digest. |
| `rollback_hint` | First-slice declaration that the operation is single-file and restorable from retained preimage material held outside the receipt. |

The proposal validator must reject unknown fields, duplicate provenance IDs, invalid operation/path combinations, absent or mismatched preconditions, excessive content, malformed UTF-8, unsupported target classes, and a proposal whose provenance is not a subset of the decision context’s provenance.

## 5. Authorization Boundary

**FACT.** Existing approval lifecycle semantics prove that EAG already understands exact-request matching, expiry, reservation, and one-time consumption, but only for commands.[7]

**RECOMMENDATION.** Authorization must occur **after** proposal policy validation and **before** `CapabilityRuntime.execute()`:

```text
validated ChangeProposal
  → MutationPolicyValidator
  → MutationAuthorizationService.issue()
  → AuthorizedChange (one-time, proposal-digest bound, expiring)
  → AuthorizedWorkspaceCapability.request_from_authorized_change()
  → CapabilityRuntime.execute()
```

`AuthorizedChange` should contain `authorization_id`, `proposal_digest`, `workspace_root_fingerprint`, `repository_snapshot_fingerprint`, approved operation/path, issued/expiry timestamps, authorizer identity/policy version, and lifecycle state `APPROVED → RESERVED → CONSUMED | EXPIRED | REJECTED`.

The authorization service must compare the proposal digest and current state exactly at reserve/consume time. A `CapabilityRequest` generated by the adapter must include only opaque authorization ID, proposal digest, and an internal sealed reference—not a free-form LLM path/content mapping. The workspace capability must refuse a mutation request without consumed authorization. This makes the question “why was this exact file modification allowed?” answerable through a proposal digest, policy decision, authorization record, and receipt.

## 6. Allowed Operations

**RECOMMENDATION.** The first G2.3 slice should allow only two single-file text operations.

| Operation | Allowed conditions | Explicit exclusions |
|---|---|---|
| `CREATE_UTF8_TEXT` | Target does not exist; parent already exists or is a policy-approved safe directory; bounded UTF-8 content; target passes sensitive-file policy. | Directory creation by default, overwrite, delete, rename, binary creation, hidden/system paths. |
| `REPLACE_UTF8_TEXT` | Target exists as a regular, non-symlink, safe UTF-8 text file; expected pre-fingerprint matches; size/content bounds pass. | Patches with fuzzy context, append-only mode, partial edit DSL, delete, rename, chmod, symlink, binary or oversized modification. |

**RECOMMENDATION.** Do not allow delete, rename, move, copy, recursive directory operations, executable permission changes, repository commands, commits, branches, checkout, networking, arbitrary command execution, or automatic tests in G2.3’s first slice.

## 7. Workspace Safety

**FACT.** `WorkspaceRuntime` has root identity, lock state, a resolver, events, and snapshots, but current write authorization is not proposal-bound.[3]

**RECOMMENDATION.** An authorized mutation must require all of the following before a write:

1. An opened workspace in a mutation-allowed mode, with the workspace root canonicalized once.
2. A workspace-root fingerprint and repository snapshot fingerprint equal to the proposal/authorization bindings.
3. A current workspace lock exclusive to the mutation attempt.
4. A complete preflight manifest for the sole target path and a before-set of allowed changed paths equal to the singleton target path.
5. Target class `regular file` for replacement or `absent` for creation; no implicit directory creation unless separately approved in a later milestone.
6. Explicit per-operation byte, line, file-count, and aggregate run-change limits.
7. An after-state manifest that proves only the authorized target changed.

A workspace mutation must be blocked if the workspace is closed, root identity changed, preflight finds unapproved concurrent target modification, the target has changed since the proposal snapshot, or the requested path is outside the bounded workspace scope.

## 8. Path and Symlink Safety

**FACT.** `PathResolver` checks whether a resolved path is inside the configured root.[8]

**INFERENCE.** Resolution alone is necessary but insufficient for mutation safety: a file can change class after preflight, and a write path should not rely on an implicit creation path or follow an unexpected symlink.

**RECOMMENDATION.** G2.3 must perform both lexical and filesystem checks:

| Check | Required outcome |
|---|---|
| Input format | Require a normalized relative `PurePosixPath`; reject absolute paths, `..`, empty components, NUL, platform drive prefixes, and ambiguous separators. |
| Root confinement | Resolve only from the canonical workspace root; require result to remain under root. |
| Parent chain | `lstat` each existing parent; reject any symlink, device, FIFO, socket, mount escape, or non-directory parent. |
| Target class | `lstat` target; reject symlink, directory, special file, and hard-link policy exceptions. A create target must be absent. |
| TOCTOU defense | Hold workspace lock; capture target inode/device/mtime/fingerprint at preflight; recheck immediately before atomic write and immediately after. |
| Absolute host paths | Never carry them in provider prompts, events, receipt, memory, or generic gateway traces. Use workspace-relative logical paths only. |

## 9. Sensitive-File Policy

**FACT.** G2.2 already has a fail-closed sensitivity policy for repository context, including environment, key/certificate, credentials, secrets, binary, oversized, ignored, unreadable, and non-UTF-8 material.[17]

**RECOMMENDATION.** G2.3 must depend on the same policy vocabulary but use a stricter mutation decision: a path excluded from read context is also excluded from create/replace mutation. The policy should reject `.git/**`, `.env`, `.env.*`, private keys, certificates, SSH material, credential/secrets directories, OS/system paths, package-manager lock or generated-cache paths unless expressly whitelisted later, hidden control files, binary files, oversized text, and content matching configured credential patterns.

No secret detector should emit matched values. Policy violations may report stable code, relative logical path only when safe, file class, and remediation category. The proposal content itself must not appear in events, logs, `MutationReceipt`, approval records, reflection, or memory.

## 10. Patch/Edit Strategy

| Option | Determinism / conflict behavior | Observability / rollback | LLM reliability and cost | First-slice assessment |
|---|---|---|---|---|
| A. Unified patch | Context/fuzz rules can be ambiguous; patch can partially apply. | Diff is familiar but partial application and conflict resolution complicate receipts. | Token-efficient for small changes, but fragile anchors. | Defer. |
| B. Structured edit operations | Deterministic only with robust anchors, uniqueness rules, and an edit grammar. | Good field-level receipts but substantial validator surface. | More compact than full files; prone to stale/ambiguous anchors. | Defer. |
| C. Full-file replacement | Exact pre-fingerprint plus exact proposed content is deterministic. | Straightforward pre/post hashes, atomic single-file replacement, and compensation. | More tokens; bounded by small safe files. | **Recommended for first slice.** |
| D. Hybrid | Can optimize later by selecting representation by policy. | Requires supporting every failure mode of A–C. | Flexible but broad. | Future evolution after reliable receipts/tests. |

**RECOMMENDATION.** Use **C: full-file replacement** for one bounded file in G2.3’s first slice. The cost is justified by a small maximum file/content budget and by exact stale-state detection. A future G2.3.x may add structured anchored edits after it has deterministic unique-anchor policy, patch application tests, and equivalent receipt semantics. The “patch synthesis” milestone title therefore means bounded, auditable source change synthesis—not a requirement to start with unified diff application.

## 11. Preconditions

**RECOMMENDATION.** Precondition validation is a deterministic gate before authorization and again immediately before write.

| Precondition | `CREATE_UTF8_TEXT` | `REPLACE_UTF8_TEXT` |
|---|---|---|
| Target existence | Must be absent. | Must exist as safe regular text file. |
| Target pre-fingerprint | Must be `None`. | Must equal proposal’s SHA-256-like content fingerprint. |
| Workspace/repository state | Must equal authorization bindings. | Must equal authorization bindings. |
| File class / sensitivity | Must pass absent-target and path policy. | Must pass regular-text and path/content policy. |
| Size | Proposed content below max. | Existing and proposed content below max. |
| Concurrency | Parent/target state unchanged while locked. | Parent/target state unchanged while locked. |
| Provenance | Proposal IDs subset of context provenance. | Proposal IDs subset of context provenance. |

A mismatch must fail closed, consume no authorization, perform no write, emit a sanitized rejection event, and yield a failure receipt with no content payload.

## 12. MutationReceipt

**RECOMMENDATION.** Create an immutable `MutationReceipt` for every terminal mutation attempt—success, policy rejection, authorization rejection, stale precondition, write failure, or verification failure.

| Field group | Required content | Sensitive-content rule |
|---|---|---|
| Identity | `mutation_id`, `run_id`, `proposal_id`, `authorization_id`, timestamp, receipt schema version. | No raw decision/prompt. |
| Scope | Relative target path, operation, proposal digest, policy/authorization versions. | No absolute path. |
| State | Pre/post fingerprint, pre/post existence, target class, snapshot/repository/workspace fingerprints. | No raw file content. |
| Change metrics | Bytes before/after, bytes changed, line delta, bounded diff-summary category. | No full diff. |
| Authorization | Decision outcome, rule IDs, approved scope digest, consumed state. | No credentials or approver secrets. |
| Result | Success/failure code, sanitized failure reason, duration, verification summary. | No stack trace or source payload. |
| Rollback | Checkpoint reference or compensation status/reference. | No embedded preimage. |

The receipt should be linkable to a later `ChangeSet` but should not force the existing ChangeSet model to become the live authorization record. A receipt is per mutation attempt; a ChangeSet is broader historical aggregation.[10]

## 13. Rollback and Failure Handling

**FACT.** Safety runtime has inspection/checkpoint/rollback concepts, but it is not wired into Coordinator’s direct capability execution path.[9]

**RECOMMENDATION.** The first slice should be deliberately single-file and use **atomic per-file mutation plus conditional compensating rollback**, not claim a multi-file transaction.

1. Preflight captures a safe temporary preimage outside the provider boundary and a before fingerprint.
2. The write uses a temporary file in the same approved directory, durable flush where supported, and atomic replacement only after all preconditions recheck.
3. A successful write receives a receipt before postcondition verification begins.
4. On verification failure, automatic restoration is allowed only when the target still has the expected post-fingerprint and the authorization’s rollback policy explicitly permits it. Otherwise the system emits a failed receipt and requires human recovery.
5. Any partial write, permission error, stale target, unexpected extra path, policy error, authorization error, provider failure, or capability failure ends the run without a second mutation attempt.

| Failure | Required behavior |
|---|---|
| Invalid proposal / policy rejection | No authorization, no write, rejection receipt/event. |
| Authorization expired/mismatch | No write; release reservation where applicable. |
| Stale precondition / concurrent change | No write; invalidate proposal/context and emit stale-state receipt. |
| Write failure before atomic replace | No target mutation expected; record failure. |
| Write failure/ambiguity after replace | Inspect target fingerprint; conditional compensation only if safe. |
| Verification failure | Produce receipt; conditional rollback only under exact post-state match; otherwise stop. |
| Provider failure | No proposal/authorization/mutation; no retry hidden inside mutation layer. |
| Capability failure | Consume/release authorization according to explicit terminal policy; emit receipt. |

## 14. Verification Boundary

**RECOMMENDATION.** Verification is deterministic and bounded in first slice. It begins after the receipt’s immediate post-write state capture, not as a free-form model judgment.

Minimum verification:

1. Re-resolve and `lstat` the target; require the expected class and root confinement.
2. Read it through the safe text policy and require post-fingerprint equality with proposal content fingerprint.
3. Recompute a bounded manifest/diff and require the changed-path set equals the authorized singleton path.
4. Check declared deterministic postconditions such as expected existence, expected fingerprint, bounded UTF-8 decode, and a whitelisted parser/static check for the target language if implemented without shell.
5. Recompute repository/workspace state and invalidate stale G2.2 context for any later proposal.

Shell-driven test execution, package installation, network calls, automatic Git status repair, and arbitrary LLM review are outside this boundary. The first EBS-015 fixture should use a deterministic textual/AST postcondition so it needs no shell.

## 15. Event and Observability Model

**RECOMMENDATION.** Add typed, redacted events with IDs/digests/counts only. Events must not contain raw provider output, prompt, proposed file content, preimage, diff body, credentials, absolute paths, or secret matches.

| Event | Safe payload |
|---|---|
| `ChangeProposalCreated` | proposal/run/decision/plan-step IDs, operation, relative safe path, size, risk, provenance count, proposal digest. |
| `ChangeProposalRejected` | policy violation code/stage, safe path where permitted, digest, reason category. |
| `MutationAuthorizationIssued/Reserved/Consumed/Rejected/Expired` | authorization/proposal digest, policy version, scope digest, lifecycle state. |
| `MutationPreconditionChecked` | outcome, snapshot/fingerprint match booleans, no content. |
| `MutationStarted` | mutation/proposal/auth IDs, one operation, one relative path. |
| `MutationCompleted` / `MutationFailed` | receipt ID, outcome, pre/post fingerprint presence, byte/line counts, sanitized failure category. |
| `MutationVerificationCompleted` | deterministic checks run, pass/fail counts, unexpected path count, receipt ID. |
| `MutationRollbackStarted/Completed/Failed` | receipt/checkpoint references and safe status. |

Receipt summaries may later enter reflection/memory only after content redaction and with bounded metadata. G2.3 must not redesign reflection or memory; it merely defines a safe handoff contract.[15] [16]

## 16. EBS-015 — Governed Patch Synthesis

**RECOMMENDATION.** Design EBS-015 as a tiny, controlled fixture benchmark named **EBS-015 — Governed Patch Synthesis**.

| Element | Design |
|---|---|
| Fixture | A small isolated repository with one safe UTF-8 module and a deterministic contract file. Example request: add one required literal field to a tiny article response helper. |
| Context | Actual G2.2 scanner/source/index/graph/context assembly, with sensitive-path fixtures proving exclusion. |
| Decision path | Real G2.1 gateway in an explicit credentialed live lane; a deterministic non-live contract lane uses a fixed valid advisory decision. |
| Proposal | One `REPLACE_UTF8_TEXT` proposal for the intended fixture file, bounded by file/content limit and exact pre-fingerprint. |
| Authorization | Deterministic policy plus one-time scoped authorization bound to proposal, workspace, repository/context fingerprints. |
| Mutation | Authorized workspace capability only; no shell, Git, network, delete, rename, or parent-directory creation. |
| Verification | Exact target post-fingerprint, only one path changed, deterministic fixture postcondition, receipt generated. |
| Safety assertions | Zero writes outside fixture workspace, zero Git operations, zero shell operations, zero network operations, one consumed authorization, one receipt. |

The live EBS-015 lane must distinguish a provider timeout/policy rejection from a grounded mutation success. A skipped or timed-out provider result is not a benchmark pass. The deterministic lane proves enforcement; the live lane proves end-to-end grounded proposal quality only when it completes successfully.

## 17. Test Strategy

**RECOMMENDATION.** Test the mutation boundary more heavily than proposal generation.

| Test layer | Required cases |
|---|---|
| Domain/unit | Proposal canonicalization/digest, operation/path validation, size limits, provenance subset, precondition rules, receipt invariants, authorization lifecycle/exact matching. |
| Workspace safety | Root escape, absolute path, `..`, symlink parent/target, special file, race/stale precondition, hidden/system/sensitive path, binary/non-UTF-8/oversize target. |
| Authorization | Missing, expired, reused, mismatched proposal digest, mismatched root/context/repository fingerprint, attempt to construct raw mutation request. |
| Capability integration | Only authorized create/replace reaches the adapter; no delete/rename/Git/shell request can execute. |
| Atomicity/rollback | Temporary-write failure, post-write verification failure, safe compensation, unsafe external modification blocks automatic rollback. |
| Events/receipts | Stable codes, relative paths only, no content/secrets/prompts, correct lifecycle ordering. |
| Chief integration | Existing non-mutation plans retain G2.0 behavior; mutation steps require explicit proposal gate; no direct Coordinator bypass. |
| EBS-015 deterministic | Full fixture flow with fixed decision/proposal, one permitted file changed, postcondition/receipt verified. |
| EBS-015 live | Explicit opt-in only; real gateway/provider; no mocks at repository/context/gateway/proposal-policy/authorization/mutation/verification boundaries. |
| Regression | Full pytest, autonomous suite, normal EBS suite, G2.2 context tests, gateway policy tests, Ruff, MyPy. |

## 18. Risks

| Risk | Impact | Design mitigation |
|---|---|---|
| LLM emits malicious or malformed content | Unsafe or irrelevant source change. | Treat proposal/content as untrusted; strict schema, provenance, content/size/path limits, deterministic authorization. |
| Stale context or concurrent editor | Overwrites a newer file. | Proposal pre-fingerprint, workspace/repository fingerprint binding, lock, immediate recheck. |
| Symlink / traversal bypass | Write outside workspace. | Canonical root, lexical validation, `lstat` parent chain/target, safe atomic path handling. |
| Sensitive file or secret leakage | Data exposure or credential modification. | Shared fail-closed sensitivity policy; no content in events/receipts; deny restricted targets. |
| Partial write or verification failure | Broken target state. | Single-file atomic replacement, receipt, conditional compensation, explicit stop. |
| Capability bypass | LLM obtains direct write path. | Generate `CapabilityRequest` only from consumed authorization; adapter rejects raw requests. |
| Provider unreliability | Live benchmark cannot establish acceptance. | Separate deterministic enforcement lane from explicit, controlled live acceptance lane; do not mark timeout as pass. |
| Scope expansion | Unsafe changes become included prematurely. | Two-operation allowlist and explicit non-goals. |

## 19. Non-Goals

G2.3 first slice does **not** introduce arbitrary shell commands, direct LLM file writes, unrestricted filesystem access, delete/rename/move/copy operations, directories/recursive edits, Git mutation, commits, pushes, branches, network access, credentials access, code execution, package installation, test-running shell commands, automated review approval, bulk changes, multi-file transactions, new workers, scheduler redesign, gateway redesign, planner replacement, or a persistent editing agent.

It does not treat G2.2’s unresolved EBS-014 live acceptance as passed and does not redesign repository context selection, Engineering Memory, Reflection, Scheduler, Chief, Coordinator, or the G2.1 governed gateway.

## 20. Migration Path

**RECOMMENDATION.** Introduce G2.3 incrementally and preserve legacy paths until explicit mutation wiring is enabled.

1. Add pure proposal/authorization/receipt domain contracts and deterministic validators with no runtime mutation.
2. Add a dedicated safe mutation adapter behind `CapabilityRuntime`, initially unavailable unless explicitly composed.
3. Add a `MutationProposalCoordinator` boundary that consumes a validated `Plan` and produces proposals; do not globally change `DecisionToPlanTranslator`.
4. Add a single opt-in composition path to canonical autonomous construction for designated mutation plans only; retain existing read-only/non-mutation behavior unchanged.
5. Add G2.3-specific events, receipts, and deterministic fixture tests.
6. Add EBS-015 deterministic lane, then separately authorize a credentialed live lane.
7. Only after sustained receipt/verification evidence consider structured edits, multi-file atomic groups, additional parsers, or approval UX.

## 21. Definition of Done

G2.3 first-slice implementation is done only when all of the following hold:

- A validated decision and Plan can produce a typed, bounded `ChangeProposal` without granting direct mutation authority.
- Exactly `CREATE_UTF8_TEXT` and `REPLACE_UTF8_TEXT` are supported; all other mutations are rejected.
- Proposal policy enforces paths, sensitivity, size, provenance, preconditions, and stale-state binding deterministically.
- Authorization is one-time, proposal-digest-bound, expiry-aware, and consumed before dispatch through `CapabilityRuntime`.
- The mutation adapter cannot execute a raw `CapabilityRequest` with model-controlled path/content.
- Root confinement, path traversal, symlink, file-class, sensitive-file, binary, and oversized-file checks fail closed.
- Every terminal attempt emits a redacted immutable `MutationReceipt` and lifecycle events.
- One target file is the only permitted mutation, verified by before/after manifest/fingerprint checks.
- Atomic write and documented conditional compensation behavior are tested.
- Git, shell, network, credentials, delete, rename, and commit/push remain unavailable.
- EBS-015 deterministic fixture passes; live EBS-015 is only accepted when an explicitly authorized real-provider run completes end-to-end.
- Existing G2.0, G2.1, and G2.2 regressions remain green.

## 23. Design Decision Summary and Status

**RECOMMENDATION.** Implement G2.3 as a narrow single-file, full-content replacement/create capability with explicit proposal, policy, authorization, receipt, and verification contracts. Do not start with unified patches, bulk/multi-file edits, Git operations, or shell-based verification.

**FACT.** G2.3.1 now supplies the isolated `src/eag/mutation` governed mutation foundation: immutable proposal, policy, authorization, atomic single-file write, receipt, lifecycle events, and deterministic EBS-015 fixture. It intentionally does **not** connect the new boundary to LLM output, Chief, Coordinator, Planner, the gateway, `CapabilityRuntime`, reflection, memory, or a live benchmark.[3] [5] [6] [7] [9] [10]

**INFERENCE.** The lowest-risk next step is to introduce a deterministic decision-to-proposal translation seam outside `ChangeProposal`, retaining the existing policy and one-time authorization gates. It must not add another generic editing subsystem or grant the model direct filesystem authority.

```text
G2.3_RECON=COMPLETE
G2.3_DESIGN=COMPLETE
G2.3.1_IMPLEMENTATION=COMPLETE
G2.3.2_IMPLEMENTATION=NOT_STARTED
G2.3_COMMIT=NOT_PERFORMED
G2.3_PUSH=NOT_PERFORMED
G2.3_TAG=NOT_CREATED
```
