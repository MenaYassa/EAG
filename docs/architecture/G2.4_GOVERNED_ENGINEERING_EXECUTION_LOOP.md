# EAG G2.4 — Governed Engineering Execution Loop

**Design date:** 21 August 2026
**Audited baseline:** [`v2.3.2-g2.3.2`](https://github.com/MenaYassa/EAG/tree/v2.3.2-g2.3.2) at `84d745314f71d532c89700bc89340412a114f78d`
**Status:** **G2.4.1 state-machine foundation and G2.4.2 trusted verification boundary are implemented and validated. G2.4.3–G2.4.5 are not started.**
**Author:** Manus AI

> **Safety thesis — RECOMMENDATION.** G2.4 should not turn a plan, reflection, or LLM response into an execution authority. It should add a deterministic execution-state controller that selects the next permitted operation from typed evidence, while preserving the existing `EngineeringDecision → ChangeProposal → policy → one-time authorization → atomic mutation → receipt` boundary for every individual mutation.

## 1. Executive Summary

**FACT.** G2.3.2 provides a narrow, public, one-shot workflow: a governed gateway returns an `EngineeringDecisionResult`; the translator derives at most one `ChangeProposal`; and `GovernedMutationRuntime` applies the existing G2.3.1 policy, authorization, atomic write, and receipt path. The workflow has terminal failure classification, but it neither loops nor replans. See `src/eag/chief/intelligence/gateway/mutation_workflow.py`.

**FACT.** EAG separately has an `AutonomousLoopRuntime` that iterates a legacy Chief/Coordinator plan-execution path, reflects on the result, stores reflection memory, and uses a deterministic completion engine to stop, continue, replan, abort, or request approval. The canonical autonomous factory does **not** compose repository context assembly, the governed gateway, or the G2.3.2 mutation workflow. See `src/eag/autonomous/runtime.py` and `src/eag/autonomous/factory.py`.

**INFERENCE.** The missing capability is not merely “run twice.” The repository lacks a persistent, deterministic, governed execution ledger that binds each iteration’s repository evidence, decision, proposal, authorization, mutation receipt, objective verification, reflection, budget consumption, and terminal reason.

**RECOMMENDATION.** G2.4 should introduce a new governed-loop composition rather than redirecting the existing generic `CapabilityRuntime` path into mutation. The first increment should be a state-machine and immutable execution-context contract; it should not yet make arbitrary plans, generic capability metadata, or LLM outputs executable.

| Topic | Current evidence | G2.4 design conclusion |
|---|---|---|
| Single mutation | **FACT:** G2.3.2 composes exactly one gateway decision, one proposal, and one receipt. | **RECOMMENDATION:** Preserve one proposal and one authorization per governed iteration. |
| Existing autonomous iteration | **FACT:** `AutonomousLoopRuntime` owns max-iteration looping, reflection, memory, completion, recovery, and approval. | **RECOMMENDATION:** Reuse selected concepts, not its generic capability execution path, for G2.4. |
| Objective verification | **FACT:** mutation postcondition verifies exact written content; legacy `DefaultValidator` only evaluates generic step success and may retry. | **RECOMMENDATION:** Add a first-class deterministic engineering verification contract. |
| Continuation control | **FACT:** current completion uses `RunResult`, reflection score, iteration count, and critical findings. | **RECOMMENDATION:** State transitions must be selected by deterministic transition guards over typed evidence and budgets. |
| Live acceptance | **FACT:** G2.3.2 implementation is complete, while EBS-015 live acceptance is pending. | **RECOMMENDATION:** G2.4 begins with deterministic fixtures and does not depend on a new live-provider call. |

See `src/eag/mutation/models.py`.

See `src/eag/mutation/runtime.py`.

**FACT.** G2.3.2 adds a trusted `PreservationRequirement` to an opt-in mutation-intent policy. The provider declares requirement identifiers, while trusted translation rejects replacement content that omits a configured leading protected region. ## 3. Current Architecture

### A. Current G2.3.2 governed mutation seam

```text
[FACT: separate, explicit composition only]

RepositoryContextAssembler (read-only; optional caller composition)
        |
        v
EngineeringDecisionRequest + EngineeringContext
        |
        v
GatewayRuntime.decide()
  route -> provider execution -> parse schema -> deterministic decision policy
        |
        v
EngineeringDecisionResult
        |
        v
DecisionToChangeProposalTranslator
  confined trusted reads + context/snapshot binding + preservation checks
        |
        v
ChangeProposal (untrusted, one file)
        |
        v
GovernedMutationRuntime
  validate -> authorize -> revalidate/consume -> atomic write -> postcondition
        |
        v
MutationReceipt (redacted terminal evidence)
```

**FACT.** `GatewayRuntime` emits routing, attempt, schema/policy, completion, and failure events. It performs provider routing and transport but returns a validated advisory result or safe failure; it does not write a workspace. See `src/eag/chief/intelligence/gateway/runtime.py`.

**FACT.** `GovernedDecisionMutationWorkflow.execute` calls the gateway once, translates the successful result once, and executes the resulting proposal once. Its outcome includes one gateway result and optional one proposal and receipt. It has no iteration, context refresh, memory write, reflection, or replanning loop. See `src/eag/chief/intelligence/gateway/mutation_workflow.py`.

### B. Current canonical autonomous build path

```text
[FACT: current CLI build composition]

CLI build(goal, workspace_dir)
        |
        v
LoopContext(goal, max_iterations=3)
        |
        v
create_autonomous_engineering_composition(workspace)
        |
        +--> WorkspaceRuntime + RepositoryRuntime
        +--> WorkspaceCapability + RepositoryCapability
        +--> CapabilityRuntime
        +--> DefaultPlanner + AdaptivePlanner
        +--> Coordinator + ChiefRuntime
        +--> ReflectionRuntime + MemoryRuntime
        '--> AutonomousLoopRuntime

        |
        v

        |
```

**FACT.** `create_autonomous_engineering_composition` registers generic `WorkspaceCapability` and `RepositoryCapability` in `CapabilityRuntime`; it does not compose `RepositoryContextAssembler`, `GatewayRuntime`, `DecisionToChangeProposalTranslator`, or `GovernedDecisionMutationWorkflow`. **FACT.** `Coordinator` converts every legacy `PlanStep` into a generic `CapabilityRequest` using `PlanStep.metadata`, then sends it to `CapabilityRuntime.execute`. See `src/eag/chief/runtime/coordinator.py`.

**FACT.** The `build` CLI command creates the canonical autonomous composition and calls `composition.loop.execute(LoopContext(...))`. The benchmark CLI independently wires the legacy generic capability path. See `src/eag/cli.py`.

**INFERENCE.** There are two valid but separate runtime topologies: a legacy autonomous generic-capability loop and a narrow governed one-shot mutation seam. G2.4 must bridge them intentionally rather than assuming that either is already the other.

It does not inspect governed decisions, proposals, authorizations, receipts, verification evidence, or context freshness. See `src/eag/autonomous/completion.py`.

## 5. Gap Analysis

**FACT.** A `ChiefRun` records one `RunContext`, one plan, generic step results, checkpoints, metrics, outcome, and error. `RunResult` carries a plan and generic step results. These types do not contain proposal history, mutation receipt history, verification artifacts, reflection artifacts, a repository-context chain, budget ledger, or typed governed stop reason. See `src/eag/chief/runtime/models.py`.

**FACT.** `ReflectionContext` currently accepts a `run_result`, optional review report, optional benchmark result, and metadata. `MemoryRuntime.store_reflection` stores a coarse success/failure summary from that reflection. Neither type includes governed mutation evidence. See `src/eag/reflection/models.py` and `src/eag/memory/runtime.py`.

**INFERENCE.** The minimum gap is a combination of: deterministic state machine, immutable execution state, first-class verification contract, legal failure transitions, evidence-bound replanning input, proposal/mutation/verification history, budget accounting, fresh-context policy, and typed terminal reasons.

**RECOMMENDATION.** G2.4 should treat the existing autonomous loop as precedent for iteration, reflection, memory, completion, and approval; it should treat G2.3.2 as the sole authorized per-step mutation pipeline. Neither runtime should be silently expanded into the other.

| Missing capability | Demonstrated source gap | Design response |
|---|---|---|
| Governed iteration controller | **FACT:** G2.3.2 workflow is single-shot; legacy loop has no governed workflow composition. | **RECOMMENDATION:** deterministic state machine with guarded transitions. |
| Cross-iteration ledger | **FACT:** `LoopIteration` stores identifiers, timing, and success only. | **RECOMMENDATION:** immutable iteration evidence records and execution context. |
| Objective verification | **FACT:** receipt verification only proves written content; legacy validator only handles step success/retry. | **RECOMMENDATION:** typed verification request/result distinct from mutation receipt. |
| Safe failure continuation | **FACT:** receipt failure stages exist but have no loop transition semantics. | **RECOMMENDATION:** deterministic terminal or reflection/replanning transition table. |
| Fresh evidence | **FACT:** context assembler exposes `ensure_fresh` and `rebuild_if_stale`, but the autonomous factory does not compose it. | **RECOMMENDATION:** refresh context before every new decision and reject stale proposal inputs. |
| Budget ledger | **FACT:** loop has only `max_iterations`; gateway limits apply to a single request. | **RECOMMENDATION:** explicit run-wide budget aggregate. |

## 6. G2.4 Objective

**RECOMMENDATION.** G2.4 should establish one bounded, evidence-driven trajectory of individually governed actions:

```text
Goal -> trusted context -> plan -> governed decision -> one proposal
     -> policy -> one-time authorization -> one mutation receipt
     -> objective verification -> deterministic transition
     -> reflection/replanning only when permitted -> next iteration or terminal stop
```

**RECOMMENDATION.** A G2.4 implementation is successful only when the controller can prove why it entered each state, why it continued or stopped, which bounded evidence it carried forward, and that no iteration bypassed G2.3.1/G2.3.2 policy or authorization.

## 7. Execution State Machine

### Proposed deterministic state graph

```text
[RECOMMENDATION: G2.4 state machine]

CREATED
  -> CONTEXT_ASSEMBLING
  -> PLANNING
  -> DECIDING
  -> PROPOSING
  -> APPROVAL_PENDING (only when trusted approval policy requires it)
  -> AUTHORIZING
  -> MUTATING
  -> VERIFYING
      -> COMPLETED                 [objective verification passes]
      -> REFLECTING                [verification fails and replan budget remains]
      -> FAILED                    [verification failure is not recoverable]

REFLECTING
  -> REPLANNING
  -> CONTEXT_ASSEMBLING            [new iteration, fresh evidence]
  -> FAILED                        [reflection fails or no legal next action]

Any nonrecoverable policy, authorization, provider, context, or budget failure
  -> FAILED or ABORTED

APPROVAL_PENDING -> AUTHORIZING | ABORTED
```

**RECOMMENDATION.** `CREATED`, `COMPLETED`, `FAILED`, and `ABORTED` are terminal-or-entry control states. All other states must have exactly one deterministic owner and an immutable evidence update before transition.

| State | Allowed input | Output / persisted evidence | Legal next states | Illegal transition examples | Failure behavior | Budget effect |
|---|---|---|---|---|---|---|
| `CREATED` | trusted goal and execution policy | execution ID, initial budget snapshot | `CONTEXT_ASSEMBLING`, `ABORTED` | direct `MUTATING` | invalid goal/policy aborts | none |
| `CONTEXT_ASSEMBLING` | workspace identity, goal, prior redacted evidence | snapshot/context fingerprints, truncation metadata | `PLANNING`, `FAILED` | reuse stale context for `DECIDING` | context error/staleness fails current run | one context build |
| `PLANNING` | goal, memory retrieval, prior verified evidence | non-executable plan or planning rationale | `DECIDING`, `FAILED` | planner to `AUTHORIZING` | no legal plan fails | one planning cycle |
| `DECIDING` | fresh `EngineeringContext`, trusted gateway policy | `EngineeringDecisionResult`, usage/trace | `PROPOSING`, `FAILED` | LLM-selected state transition | provider/schema/policy failure fails by default | one decision attempt and usage debit |
| `PROPOSING` | successful decision, trusted workspace state, intent policy | one proposal or sanitized translation violation | `APPROVAL_PENDING`, `AUTHORIZING`, `FAILED` | multiple proposals in G2.4 initial slice | translation failure fails | one proposal slot |
| `APPROVAL_PENDING` | validated proposal and trusted approval mode | approval request/decision | `AUTHORIZING`, `ABORTED` | approval directly mutates | denied/expired approval aborts | approval wait budget/time |
| `AUTHORIZING` | validated proposal | one proposal-bound authorization | `MUTATING`, `FAILED` | reused authorization to `MUTATING` | authorization failure fails | one authorization slot |
| `MUTATING` | validated proposal plus unconsumed authorization | redacted mutation receipt | `VERIFYING`, `FAILED` | generic capability dispatch | policy/write/postcondition failure follows receipt map | one mutation slot |
| `VERIFYING` | completed receipt, trusted verification specification | typed verification result | `COMPLETED`, `REFLECTING`, `FAILED` | receipt success equals objective success | verifier error/failure follows policy | one verification slot |
| `REFLECTING` | receipt, verification result, goal, plan/decision references, bounded context | reflection report | `REPLANNING`, `FAILED` | reflection issues new mutation | reflection failure fails | one reflection slot |
| `REPLANNING` | reflection, accumulated evidence, remaining budgets | deterministic next-step decision | `CONTEXT_ASSEMBLING`, `COMPLETED`, `FAILED` | reusing previous authorization/proposal | exhausted/no-safe-next step fails | one replan slot |
| `COMPLETED` | passed objective verification | terminal summary and evidence index | none | any new mutation | none | final |
| `FAILED` | typed failure/stop reason | terminal redacted failure record | none | automatic provider retry | none | final |
| `ABORTED` | user denial/cancel or safety stop | terminal abort record | none | resume without a new governed run | none | final |

**RECOMMENDATION.** The LLM may influence only the advisory decision payload. It must not choose the state, skip a guard, mark verification successful, consume authorization, reset a budget, or select a terminal outcome.

## 8. Execution Context

**FACT.** Existing types already cover parts of the future context: `LoopContext` covers goal and max iterations; `RunContext` covers run identity and metadata; `EngineeringDecisionRequest/Result` cover context, request policy, usage, trace, and policy violation; `ChangeProposal`, `MutationAuthorization`, and `MutationReceipt` cover one governed mutation; `ReflectionContext/Report` and `MemoryEntry` cover reflection and memory.

**RECOMMENDATION.** Do not mutate or overload those models. Add a minimal immutable `GovernedExecutionContext` and append-only `GovernedIterationRecord` that reference existing artifacts by value or redacted identity.

| Context field | Existing reusable contract | G2.4 need |
|---|---|---|
| execution/run ID and goal | **FACT:** `LoopContext.loop_id`, `RunContext.run_id`, and `ChangeProposal.run_id` exist. | **RECOMMENDATION:** one `execution_id`, one stable goal, and per-iteration IDs. |
| iteration number | **FACT:** `LoopIteration.iteration_number` exists. | **RECOMMENDATION:** retain it and bind each evidence record to it. |
| fresh repository evidence | **FACT:** context assembler exposes snapshot and context fingerprints. | **RECOMMENDATION:** persist fingerprints and truncation status, never raw unrestricted repository content. |
| current plan/decision | **FACT:** `Plan` and `EngineeringDecision` exist. | **RECOMMENDATION:** store immutable references/digests plus current phase. |
| active proposal and authorization | **FACT:** proposal and authorization models exist. | **RECOMMENDATION:** allow at most one active pair in the initial model. |
| mutation and verification result | **FACT:** receipt exists; objective verification result does not. | **RECOMMENDATION:** add a typed verification result reference. |
| reflection and memory | **FACT:** report and memory entry IDs exist. | **RECOMMENDATION:** record IDs and sanitized summary metadata. |
| budget / stop reason | **FACT:** per-request gateway policy and loop max iterations exist. | **RECOMMENDATION:** add a typed aggregate budget ledger and typed stop reason. |

**RECOMMENDATION.** The execution context must remain content-redacted by default. It should retain fingerprints, IDs, policy versions, counters, and bounded summaries, not raw provider text, credentials, or unrestricted file content.

## 9. Verification Model

**FACT.** A completed `MutationReceipt` requires `verification_passed=True`, but that verification is fingerprint-based postcondition verification of the proposal’s expected file content. It does not prove the engineering objective. See `src/eag/mutation/models.py` and `runtime.py`.

**FACT.** `DefaultValidator` returns `CONTINUE` for a successful generic capability result, retries a failed step up to its local limit, then aborts. It is not an objective verifier and is not tied to G2.3.2 evidence. See `src/eag/chief/runtime/validator.py`.

**RECOMMENDATION.** Introduce a future `VerificationRuntime` with a typed, trusted `VerificationRequest` and immutable `VerificationResult`. It must distinguish mutation success, verification success, and objective success.

| Result layer | Meaning | Required evidence |
|---|---|---|
| Mutation success | **FACT:** the bounded write completed and the proposal postcondition matched. | `MutationReceipt.result == COMPLETED` and receipt postcondition flag. |
| Verification success | **RECOMMENDATION:** trusted checks against a declared verification specification passed. | verifier ID/version, bounded observations, pass/fail, sanitized reason. |
| Objective success | **RECOMMENDATION:** deterministic completion policy accepts passed verification against the goal’s declared acceptance conditions. | verification result plus budget/state evidence. |

**RECOMMENDATION.** G2.4.2 should begin with injected deterministic verification doubles and fixture-specific pure checks. It must not let an LLM submit arbitrary shell commands, test commands, network calls, or Git operations as verification.

## 10. Failure Model

**RECOMMENDATION.** A failure transition must be chosen from a typed failure map, never from a free-form LLM recommendation.

| Observed failure | Evidence source | Proposed transition | Rationale |
|---|---|---|---|
| Provider timeout/failure | `EngineeringDecisionResult.error` | `FAILED` with `PROVIDER_FAILED` | Avoid silent automatic retries and avoid inventing new decisions. |
| Schema or decision-policy rejection | gateway result / violation | `FAILED` with `POLICY_REJECTED` | A rejected advisory result must not become a replanning bypass. |
| Translation failure | sanitized translation violation | `FAILED` with `TRANSLATION_FAILED` | No proposal exists to authorize or repair. |
| Mutation policy/authorization failure | receipt/failure stage | `FAILED` with corresponding typed reason | Preserves policy and one-time authorization authority. |
| Atomic write/postcondition failure | receipt | `FAILED` with `MUTATION_FAILED` or `POSTCONDITION_FAILED` | Do not retry an authorization or mutate again implicitly. |
| Objective verification failure | future `VerificationResult` | `REFLECTING` only if a replan budget remains | A later iteration must create a new decision, proposal, and authorization. |
| Reflection failure | reflection runtime error | `FAILED` | Reflection must not be silently skipped. |
| Budget exhausted | deterministic budget ledger | `FAILED` with `BUDGET_EXHAUSTED` | Termination is deterministic. |
| Human denial/expiry | approval decision | `ABORTED` | Approval never becomes an authorization bypass. |

**RECOMMENDATION.** “Replanning” must never mean replaying the same proposal, reusing an authorization, editing provider output, or automatic repair. It means returning to fresh-context assembly and producing a newly governed decision under remaining budgets.

## 11. Reflection/Replanning Model

```text
[RECOMMENDATION: only verification failure can enter the first recovery loop]

Completed mutation receipt
        |
        v
Trusted objective verification -- PASS --> COMPLETED
        |
        FAIL (remaining replan budget only)
        v
ReflectionContext adapter
  goal + plan/decision IDs + proposal digest + receipt + verification result
  + bounded fresh repository context + previous redacted iteration evidence
        |
        v
ReflectionRuntime -> ReflectionReport -> MemoryRuntime
        |
        v
Deterministic ReplanningPolicy
        |
        +--> stop/fail/abort
        '--> CONTEXT_ASSEMBLING for a new governed iteration
```

**FACT.** `ReflectionRuntime` only publishes started/completed/failed events around its engine. It does not own replanning. `MemoryRuntime.store_reflection` only stores a reflection-derived entry. See `src/eag/reflection/runtime.py` and `src/eag/memory/runtime.py`.

**RECOMMENDATION.** Add a `GovernedReflectionContext` adapter rather than changing `ReflectionContext` immediately. The adapter should construct the existing reflection input with a synthetic bounded run-result view and include redacted metadata: iteration, goal digest, decision digest, proposal ID/digest, receipt fields, verification result, context fingerprints, and prior iteration summaries.

**RECOMMENDATION.** A future `ReplanningPolicy` should be deterministic and produce only `STOP`, `FAIL`, `REQUIRE_APPROVAL`, or `CONTINUE_WITH_FRESH_DECISION`. `AdaptivePlanner` may advise a new non-executable plan from this evidence; it cannot authorize or execute a mutation.

## 12. Bounded Execution

**FACT.** The existing autonomous loop has `max_iterations`; the gateway has per-request attempt, timeout, token, cost, and fallback settings. Those limits are not aggregated into one governed trajectory budget.

**RECOMMENDATION.** The minimum G2.4 aggregate budget is below. Every debit is recorded before the next transition.

| Budget | Initial recommended boundary | Deterministic terminal reason |
|---|---|---|
| iterations | `max_iterations >= 1` | `ITERATION_BUDGET_EXHAUSTED` |
| decisions | at most one gateway decision per iteration | `DECISION_BUDGET_EXHAUSTED` |
| proposals | at most one translated proposal per iteration | `PROPOSAL_BUDGET_EXHAUSTED` |
| authorizations/mutations | at most one each per iteration | `MUTATION_BUDGET_EXHAUSTED` |
| verification attempts | at most one per completed receipt per iteration | `VERIFICATION_BUDGET_EXHAUSTED` |
| reflections/replans | zero or one after each eligible verification failure | `REPLAN_BUDGET_EXHAUSTED` |
| provider tokens/cost | sum redacted `GatewayUsage` across decisions | `PROVIDER_BUDGET_EXHAUSTED` |
| wall-clock duration | trusted deadline or elapsed limit | `TIME_BUDGET_EXHAUSTED` |
| failures | bounded failure count by category | `FAILURE_BUDGET_EXHAUSTED` |
| approval wait | optional trusted timeout | `APPROVAL_EXPIRED` |

**RECOMMENDATION.** Provider failure must not consume a mutation budget because no proposal exists, but it should consume a decision attempt and may consume time/cost actually recorded by the gateway.

## 13. Multi-Step Mutation Model

**RECOMMENDATION.** G2.4 should use a serial, evidence-gated model, not a batch proposal model.

```text
Iteration N: fresh context -> one decision -> one proposal -> one authorization
           -> one mutation -> one verification -> terminal or reflection

Iteration N+1: only after a legal reflection/replanning transition
           -> fresh context -> new decision -> new proposal -> new authorization
```

**FACT.** G2.3.2’s mutation intent contract is limited to exactly one future bounded file mutation and no dependencies in its initial slice. Its workflow contains one optional proposal and one optional receipt.

**RECOMMENDATION.** Each mutation remains individually proposed, policy-validated, authorization-bound, executed, receipt-producing, and objectively verified. G2.4 must not introduce a “ten proposals then ten mutations” bypass.

## 14. Event Model

**FACT.** Existing event families already cover repository-context assembly/freshness, gateway request/routing/attempt/policy/completion/failure, mutation proposal/authorization/start/completion/rejection/failure, Chief planning/execution/validation/run completion, and reflection started/completed/failed.

**FACT.** `EventBus` is in-process and synchronous; it dispatches only exact event classes and provides no persistence, durability, replay, or cross-process ordering contract. See `src/eag/events/bus.py`.

**RECOMMENDATION.** Reuse existing granular gateway, context, mutation, and reflection events. Add only execution-controller events that express cross-component state and are not otherwise observable.

| Proposed G2.4 event | Why it is needed | Reused evidence |
|---|---|---|
| `GovernedExecutionStarted` | identifies one trajectory and its budgets | execution ID, goal digest, policy versions |
| `EngineeringIterationStarted` | separates serial governed iterations | execution ID, iteration, fresh snapshot/context fingerprints |
| `GovernedProposalTranslated` | distinguishes translation from `MutationProposed`, which occurs at mutation validation | decision digest, proposal ID/digest, redacted target metadata |
| `VerificationStarted` / `VerificationCompleted` | objective verification has no existing event family | verification ID/version, status, sanitized summary |
| `ReplanningStarted` / `ReplanningCompleted` | makes deterministic continuation observable | prior iteration ID, transition reason, next action |
| `EngineeringExecutionCompleted` | records success terminal reason and final evidence index | stop reason, iterations, budgets consumed |
| `EngineeringExecutionAborted` | records denied/user/safety terminal reason | abort reason, active state, safe counters |

**RECOMMENDATION.** Every proposed event must carry `execution_id`, `iteration`, and an event sequence number generated by the state controller. The event bus itself is not a source of durable execution state.

## 15. Memory Integration

**FACT.** `MemoryRuntime` can store and retrieve reflection-derived experience, and `Coordinator` can use one relevant experience to adapt a base plan. Memory entries currently store reflection ID, a coarse summary, tags, and score/outcome metadata.

**RECOMMENDATION.** G2.4 should retrieve memory only during planning/replanning and write memory only after a terminal iteration reflection. Persist redacted, verified lessons; do not store raw provider content, proposed file content, credentials, or unverified claims.

**RECOMMENDATION.** Add execution provenance to future memory metadata: execution/iteration ID, decision/proposal/receipt IDs, verification status, context fingerprint, and policy versions. This is additive evidence, not a MemoryRuntime redesign.

## 16. Adaptive Planner Integration

**FACT.** `AdaptivePlanner.create_plan` delegates to its base planner. `AdaptivePlanner.plan` rewrites a `Plan` with rule-based `PlanStep` insertions and returns an `AdaptivePlan` plus `PlanningDecision`. It has no authorization or filesystem interface. See `src/eag/adaptive/planner.py`.

**RECOMMENDATION.** Use `AdaptivePlanner` only behind a future `ReplanningAdapter`:

```text
Verified evidence + reflection + memory retrieval
        -> ReplanningAdapter
        -> AdaptivePlanningContext / non-executable Plan
        -> deterministic state controller
        -> fresh governed decision request
```

**RECOMMENDATION.** The planner may suggest a next non-executable planning context. It must not receive `MutationAuthorization`, call `GovernedMutationRuntime`, mutate workspace state, or select a state transition.

## 17. Human Approval Seam

**FACT.** The existing autonomous loop can pause at `WAITING_APPROVAL` after completion evaluation. That approval is not wired to the G2.3.1 authorization boundary.

**RECOMMENDATION.** G2.4 should introduce trusted approval policy modes: `AUTOMATIC`, `REQUIRE_APPROVAL`, and `DENIED`. The seam belongs after a proposal has passed deterministic translation/policy prerequisites and before `GovernedMutationRuntime.authorize`.

**RECOMMENDATION.** An approval decision permits entering `AUTHORIZING`; it does not create an authorization, mutate a file, change policy, or alter proposal content. A denial leads deterministically to `ABORTED`.

## 18. Benchmark Strategy

**FACT.** `BenchmarkRunner` already prepares a disposable fixture workspace, executes an injected benchmark executor, evaluates a result, and cleans the workspace in `finally`. See `src/eag/benchmark/runner.py`.

**RECOMMENDATION.** The first G2.4 benchmark must be deterministic and use a scripted/fake governed gateway plus deterministic verifier and reflection engine. It must not require a live provider.

|---|---|

**RECOMMENDATION.** A future live lane should be separate, opt-in, one provider call per authorized execution, and attempted only after the deterministic benchmark is green. It must not redefine the deterministic contract or be used to force acceptance.

## 23. Definition of Done

**RECOMMENDATION.** G2.4 is not complete because “the agent ran twice.” It is complete only when deterministic evidence demonstrates all of the following:

1. Every state transition is validated by a pure deterministic transition guard, and illegal transitions are rejected.
2. Each iteration has a fresh or explicitly validated repository-context fingerprint before a new decision.
3. Every mutation has exactly one `ChangeProposal`, policy validation, proposal-bound one-time authorization, receipt, and deterministic postcondition verification.
4. Mutation success, objective verification success, and engineering-objective completion are distinct asserted values.
5. An objective verification failure produces reflection and exactly one legal replanning decision when budget permits.
6. Replanning produces a fresh governed decision; it never reuses a proposal or authorization.
7. Passed objective verification causes `COMPLETED` with a typed terminal reason.
8. Budget exhaustion, policy rejection, authorization failure, provider failure, and user denial cause deterministic terminal states.
9. Unsafe proposals remain blocked and cause zero out-of-workspace, Git, shell, network-mutation, or credential-access effects.
10. The deterministic isolated benchmark proves a multi-iteration failure-to-success trajectory and fixture cleanup.
11. Existing G2.3.1/G2.3.2 safety tests and legacy autonomous tests remain unchanged and green.

## 24. Migration Strategy

**RECOMMENDATION.** Introduce a separate public `create_governed_engineering_execution_composition` only after G2.4.1 through G2.4.3 are deterministically accepted. Do not replace `create_autonomous_engineering_composition` or the current `build` command in the first G2.4 increment.

**RECOMMENDATION.** Migrate in order: pure models and transition tests; trusted verification interface; reflection/replanning adapter; scripted governed composition; deterministic benchmark; only then consider an opt-in product entrypoint. Preserve direct Chief callers and the existing autonomous build path throughout.

**RECOMMENDATION.** No history rewrite, no reclassification of G2.3.2 live acceptance, and no automatic EBS-015 rerun are part of migration.

## 27. G2.4.1 Implemented Foundation

**IMPLEMENTATION FACT.** The actual state set is `CREATED`, `CONTEXT_ASSEMBLING`, `PLANNING`, `DECIDING`, `PROPOSING`, `APPROVAL_PENDING`, `AUTHORIZING`, `MUTATING`, `VERIFYING`, `REFLECTING`, `REPLANNING`, `COMPLETED`, `FAILED`, and `ABORTED`. This matches the approved design candidate set; no speculative state was added.

| From state | Actual legal next states |
|---|---|
| `CREATED` | `CONTEXT_ASSEMBLING`, `ABORTED` |
| `CONTEXT_ASSEMBLING` | `PLANNING`, `FAILED` |
| `PLANNING` | `DECIDING`, `FAILED`, `ABORTED` |
| `DECIDING` | `PROPOSING`, `FAILED` |
| `PROPOSING` | `APPROVAL_PENDING`, `AUTHORIZING`, `FAILED` |
| `APPROVAL_PENDING` | `AUTHORIZING`, `ABORTED` |
| `AUTHORIZING` | `MUTATING`, `FAILED` |
| `MUTATING` | `VERIFYING`, `FAILED` |
| `VERIFYING` | `COMPLETED`, `REFLECTING`, `FAILED` |
| `REFLECTING` | `REPLANNING`, `FAILED` |
| `REPLANNING` | `CONTEXT_ASSEMBLING`, `FAILED` |
| `COMPLETED`, `FAILED`, `ABORTED` | no legal transitions |

**IMPLEMENTATION FACT.** `GovernedExecutionContext` is a deeply immutable public value: its context and evidence metadata recursively freeze mappings, sequences, sets, and byte arrays, and external mutable aliases cannot alter stored state. It carries a stable execution ID, run ID, goal, current state, iteration, immutable `ExecutionBudget`, append-only `ExecutionTransitionRecord` history, redacted `ExecutionEvidenceRef` values, and typed stop reason. It carries references rather than full decision, proposal, authorization, receipt, verification, or reflection objects.

**IMPLEMENTATION FACT.** The aggregate `ExecutionBudget` contains exactly `max_iterations`, `max_mutations`, and `max_verifications` plus monotonic consumed counters. A non-`CREATED` public context is accepted only when its complete ledger begins at `CREATED`, uses the legal-transition matrix exactly, remains contiguous, and reaches the supplied current state. Its iteration, mutation, and verification counters must equal, respectively, legal entries into `CONTEXT_ASSEMBLING`, `MUTATING`, and `VERIFYING`; context evidence must exactly equal flattened transition evidence. No elapsed-time, provider-token, provider-cost, or retry budget was added because no compatible aggregate abstraction exists in the current runtime and those integrations are outside G2.4.1.

**IMPLEMENTATION FACT.** Actual terminal stop taxonomy is `SUCCESS`, three typed budget-exhaustion reasons, `POLICY_REJECTED`, `AUTHORIZATION_FAILED`, `PROVIDER_FAILED`, `VERIFICATION_FAILED`, `UNRECOVERABLE`, and `USER_ABORTED`. A completed execution requires `SUCCESS`; an aborted execution requires `USER_ABORTED`; a failed execution rejects both of those nonfailure reasons.

**IMPLEMENTATION FACT.** The state machine emits `GovernedExecutionStarted`, `GovernedExecutionTransitioned`, and `GovernedExecutionStopped` only after it has already produced the next immutable context. Event publication is best-effort because the existing synchronous `EventBus` lets handlers raise: observer failure cannot alter accepted transition correctness, but it can cause telemetry loss. G2.4.1 provides no durable event-delivery guarantee.

**IMPLEMENTATION FACT.** Deterministic coverage includes initial state; valid and invalid transitions; strict typed errors; terminal protection; typed stops; monotonic and exhausted budgets; rejected impossible direct reconstruction; rejected illegal, disconnected, terminal-extended, and state-mismatched histories; ledger-derived budget counts; deep alias-safe metadata/evidence immutability; event ordering; observer-failure independence; no operational-runtime imports; and EBS-016’s fake-reference two-iteration lifecycle. EBS-016 represents future decision/mutation/verification/reflection artifacts only; it invokes none of them.

**IMPLEMENTATION FACT.** Existing `LoopState`, `RunState`, `LoopContext`, `RunContext`, `LoopIteration`, mutation contracts, generic CapabilityRuntime path, autonomous factory, and G2.3.2 workflow remain unchanged. The new package is a foundation, not a new operational runtime or final governed autonomous composition.

**RECOMMENDATION.** G2.4.2 may add first-class verification only after G2.4.1 final regression acceptance. G2.4.3–G2.4.5 remain future work.

**IMPLEMENTATION FACT — G2.4.2 update (21 August 2026).** The G2.4.2 trusted verification boundary is implemented as `eag.governed_execution.verification`. It is isolated from the state machine: it returns immutable verification evidence and a pure objective assessment, but never selects, requests, or performs a state transition.

## 28. G2.4.2 First-Class Engineering Verification

**IMPLEMENTATION FACT.** G2.4.2 distinguishes three separate results. `MutationReceipt.result == completed` plus its G2.3.1 postcondition flag is **mutation success**. `VerificationResult.status == passed` is **verification success** for a trusted independent assertion. `ObjectiveAssessment.status == satisfied` is **objective success**, and the pure completion policy produces it only when both mutation success and trusted verification success hold for the same receipt identity.

| Contract | Actual G2.4.2 boundary |
|---|---|
| Trusted specification | Immutable `VerificationSpecification` selected outside provider output. It has an ID, version, confined relative target, one approved check type, and a positive byte bound. |
| Request | Immutable `VerificationRequest` binds one run, one receipt evidence object, one matching target specification, and optional same-run G2.4.1 context. |
| Result | Immutable `VerificationResult` has a verification ID, status, redacted `VerificationEvidence`, and stable typed failure code. |
| Objective policy | `ObjectiveCompletionPolicy` is a pure assessment function. It has no state-machine, reflection, replanning, mutation, or authorization authority. |
| Ledger handoff | A result produces a redacted `ExecutionEvidenceRef` of kind `VERIFICATION`; attaching it to a future state transition remains a later state-machine caller responsibility. |

**IMPLEMENTATION FACT.** The only first-slice checks are exact UTF-8 file content, expected file existence, expected absence, and an expected SHA-256 fingerprint. Each request binds one target path and a maximum readable byte size. The verifier rejects traversal, absolute paths, symlink components, outside-workspace resolution, nonregular targets, and oversize reads. It only reads a confined target; it contains no command, Git, network, credential, provider, workspace-write, authorization, or mutation operation.

**IMPLEMENTATION FACT.** The verifier does not accept a model assertion such as “verification passed.” There is no provider-claim field or arbitrary command field in a verification specification or request. A provider-originated string cannot become a `PASSED` result; only evaluation of the trusted typed assertion can do so.

**IMPLEMENTATION FACT.** EBS-016 now also proves that a receipt whose G2.3.1 mutation postcondition passed can fail a trusted exact-content assertion and therefore yields an objective status of `NOT_SATISFIED`. The fixture uses no real LLM, provider, shell, Git, network, credential, reflection, replanning, second mutation, or autonomous composition.

**IMPLEMENTATION FACT.** G2.4.2 does not modify G2.3.1 mutation policy/authorization/atomic write/receipt behavior, G2.3.2 preservation/gateway behavior, `AutonomousLoopRuntime`, the autonomous factory, CLI build, `Coordinator`, generic `CapabilityRuntime`, or G2.4.1 transition authority.

**RECOMMENDATION.** G2.4.3 remains the first permitted future integration of trusted verification evidence into reflection/replanning. G2.4.4 remains the future bounded governed-execution composition; neither is part of G2.4.2.

**RECOMMENDATION.** Stop after final G2.4.2 validation. A later milestone requires separate approval before adding reflection, replanning, provider, composition, generic-capability, or live-benchmark behavior.
